## Found while building (M0)

Questions the build raised. Each has a provisional answer in the code; change the code if the product owner decides otherwise.

| # | Question | Provisional answer (in the code now) |
|---|---|---|
| B1 | Is a nesting cycle checked per nesting type, or across all nesting types together? | Per type: *contains* can never loop, but a *contains* path and a *composedOf* path may cross |
| B2 | Which end does a rule's `cardinality` limit? | The source: `0..1` means a source has at most one such relationship to a matching target (e.g. at most one location). Lower bounds (`1..1`, `1..*`) cannot be enforced while editing; they become validation findings later |
| B3 | What does a `warn` relationship rule mean? | The pair is allowed but discouraged: the change is applied and a warning finding is returned. A pair matched by no rule is refused |
| B4 | What happens to nested occurrences when their parent occurrence is removed, or the nesting relationship behind them is deleted? | They move to the top level of the diagram and stay where they were on screen |
| B5 | Folders are not scenario-aware (`folder` has no `scenario_id`). Who may delete them? | Only changes in the baseline. Folders created in a scenario exist in every scenario |
| B6 | Deleting an object leaves `objectRef` properties elsewhere pointing at it | Left as they are for now; a validation rule should flag them (M3) |
| B7 | `example-repository.json` scenario edits omit `baseVersion`, which `changes.ts` requires | The tests fill it in from the state; the example should carry it |
| B8 | Must an object's name be unique only among objects of exactly its type, or also among its subtypes? | Exactly its type (`application` and `saasApplication` are checked separately) |
| B9 | When an object changes type, values the new type cannot hold | They are dropped; undo restores them |
| B10 | The query language is M1 work, but `GET …/objects?q=` is in the API now | A subset works now: `type:<key>` (subtypes included) and `folder:"<path>"` (subfolders included), joined with `AND`. Anything else gets 422. It is a strict subset of the grammar, so queries written now keep working |
| B11 | Undo: "if someone has since changed the same property, that part is skipped" | Not yet: an undo whose inverse conflicts is rejected as a whole (409). Skipping parts needs per-edit conflict handling in the engine. Undo is limited to your own changes (403 otherwise) and to once per change |
| B12 | Sign-in before OIDC (M1) | Development tokens `Bearer dev:<workspace>:<user>`, only when `CONNECTOME_DEV_AUTH=1`, and refused when `NODE_ENV=production`. Without it every API request gets 401 |
| B13 | How does a sender learn its change was confirmed on the live connection? | Through the same `committed` message every viewer gets (it carries the change id, seq and versions). Only rejections go to the sender alone. So there is one ordered stream to apply, for everyone |
| B14 | How does a browser authenticate a WebSocket, which cannot carry headers? | `POST /live/tickets` returns a signed ticket valid for 60 s, passed as `?ticket=`. Instances share `CONNECTOME_SECRET` (required in production) |
| B15 | The `interest` message (item-level subscriptions) | Accepted and ignored for now: every viewer of a repository gets all its changes for its scenario. Narrowing matters only for very large repositories |
| B16 | How does the browser get the state it runs the change engine on? | `GET …/snapshot?scenario=` returns the whole scenario as engine rows (tombstones, versions and field versions included) with the metamodel and the sequence it reflects; the live connection then opens with `?since=` that sequence. Whole-repository loading is an M0 simplification: the design limit (1M objects) cannot be loaded whole, so lazy loading through `interest` (B15) comes with the performance pass (M2) |
| B17 | How does the browser apply a baseline change while it shows a scenario? | It doesn't: which rows a scenario overrides is resolved on the server, so a change from an ancestor scenario (or one whose versions come out differently in the browser) makes the browser reload a snapshot. Before reloading, it resends its pending changes over HTTP (idempotent), so a change the snapshot already holds is never applied twice. Changes in the browser's own scenario are replayed with the same engine, actor and commit time as on the server and give identical rows |
| B18 | Every edit gets a toast with **Undo**, but undo is built from the stored inverse on the server: what if the user clicks it before the change is committed? | Undo is offered once the server has confirmed the change; until then the button is disabled. Undoing a pending change locally (before it is sent) waits for redo/undo stacks in M2 |
| B19 | A type's `defaultFolder` is a folder path. What if no folder has that path? | The new object goes into the diagram's folder. Folders are never created implicitly |
| B20 | What does the diagram editor's palette offer? | The object types the diagram type admits (a listed type admits its subtypes), abstract ones left out, in the package's order |
| B21 | How is the explorer's order stored? | A `rank` on folders, objects and diagrams set by its own edit `setRank` (not folded into the move edits), last writer wins. A move is `moveToFolder`/`moveFolder`/`updateDiagram` plus `setRank` in one change. Items of any kind can be interleaved in a folder. The first reorder in an unranked folder ranks every sibling in its current order |
| B22 | What is a group? | An object of the Essentials type `group` (Essentials 1.2.0) linked to its members by `groups`, an aggregation (S15): members stay in their folders, may be in several groups, and groups may hold groups. The explorer lists a group's members under it as references (↗) |
| B23 | How does the properties panel choose an editor? | From the property type: an optional `editor` hint (`dropdown`, `segmented`/`radio`, `rating`, `switch`, `checkbox`, `checkboxes`, `chips`; default `auto`) where it fits the data type, else automatically. A list keyed 1..n is a rating; a list of at most 4 values whose labels total at most 24 characters is a segmented control; any other list is a dropdown. A hint that does not fit the data type is ignored |
| B24 | Which items have a description? | Objects (new edit `setDescription`; `createObject` could already set it) and diagrams (`updateDiagram`). Relationships and folders have none in the model; **open**: whether relationships should get one, with `setProperties` for relationships |
| B25 | What is a property set? | A named, ordered list of a type's properties, defined on object types in the package (`propertySets`, inherited and replaced by key), so "Quarterly review" can mean different properties per type under one key that a user profile can name later. A user's own sets live in the browser until profiles exist. Essentials 1.4.0 (1.3.0 is taken by the notation slice) adds `documentation.link` and three sets on applications |
| B26 | Where are review confirmations kept? | In the properties panel and on the object (answered 2026-10-06: "confirmations on this properties panel"): `confirmations` maps a property key to who confirmed it and when, set by the edit `confirmProperties` with the commit's author and time, never a time the client chooses. A confirmation is current within its calendar quarter and lapses when the value changes. **Open** for P-4: whether `setConfirmations` (the inverse) should be refused outside undo, so nobody can write a confirmation in someone else's name |
| B27 | Who may change the metamodel, and where does a change apply? | Slice A-1: anyone who can open the repository may publish relationship rules, until roles exist (**open**: restrict to an admin role, screens.md §6 says *admins*). The metamodel is per repository, so a publish applies to every scenario at once. A publish needs the version it was edited from; a stale one is refused (409) rather than merged |
| B28 | What does a publish do to values whose property a type no longer carries, and which items have properties? | Slice A-1b: values are **kept**. A publish never rewrites stored data; the review counts the values left behind and the properties panel lists them under *Not on this type* with *Clear*. Publishing is refused when it would make stored data invalid: removing a type in use, changing a property's data type while values exist, removing a list value in use. Objects, relationships and diagrams carry properties (diagram types gained `properties`); "components" are object types. **Open**: a migration step that moves values to another property (metamodel.md §7), and whether to clear values in bulk from the review. |
| B29 | Can a matrix view hold occurrences? | No (slice V-1): only diagrams whose type is a canvas (`kind` absent or `canvas`) hold object occurrences, relationship occurrences and annotations; the engine refuses the rest, and *Occurs on ▸ Add* offers canvases only. A diagram cannot change to a type of another kind, since its definition and occurrences would no longer fit |
| B30 | Where do a matrix view's settings live? | The type's `matrix` is the default and the diagram's `definition` overrides it key by key (`rows`, `columns`, `relationships`, `create`, `groupRows`, `hideEmpty`); *Reset* removes the overrides. Rows and columns are structured scopes (a `from` filter by type, category or folder, then `steps` along relationships), evaluated by the pure package `packages/views` |
| B31 | What does clicking a matrix cell do? | An empty cell with exactly one allowed relationship type creates it at once (Undo in the toast); otherwise a popover lists the cell's relationships (select, delete) and every type the metamodel allows either way. A cell no rule allows is drawn hatched and disabled. The metamodel's connection matrix and matrix views share one grid component |
| B32 | How is a document template stored, and its sections' state? | Slice V-2: the template is the diagram type's `document` (`subject` filter and `sections`), next to `kind: "document"`, as a matrix type has `matrix`. A section is `{ key, title, component, config, required, guidance }`; patterns (`use`), locks, `allow` and regions wait for V-4/V-5. A document's `definition` holds `subject` and one key per section, so `subject` is a reserved section key. The metamodel refuses a template naming an unknown component, property, kind, relationship type or diagram type, a link to a non-canvas, or a table reading a section that is not a linked diagram |
| B33 | What does V-2 build of the component framework? | The registry in `packages/views` (`COMPONENTS`: name, whether it counts towards completeness, a pure `project` that returns the section's view model with its findings) for `heading`, `prose`, `facts`, `diagramLink` and `relationTable`, and one renderer per component in the web app. Config JSON Schemas for the designer, `export` and the other components (`list`, `matrix`, `repeater`, `sequenceLink`, `decisionLog`) come with the slices that need them |
| B34 | How do prose and mentions work? | Prose is stored as paragraphs of text runs and `{ mention: id }`, so a rename needs no rewrite and a deleted element shows as *deleted element*. Authors edit it as text where a mention reads `@[name](id)`; typing `@` opens a picker of elements by name, and, when the template allows, *Create "…" as* a type, which creates the element in the subject's folder. A chip offers *Open* and *Link to subject* with the relationship types the rules allow either way |
| B35 | Which relationships does a table bound to a linked diagram show, and in which columns? | One row per relationship drawn on that diagram whose type or kind the source names; the subject's other relationships of those kinds are the *missing* banner (*Add to context* places them, one change; *Ignore* remembers them in the section's state). A column is `direction`, `payload`, a property key, or `{ key, label, properties }`: one column over several properties (the first the row's type has), so a flow's `flow.protocol` and an interaction's `interaction.protocol` share *Protocol*. A cell whose type lacks the property shows a dash and is never required. *+ Add* creates the relationship and places it, and its counterpart if missing, on the diagram in one change |
| B36 | How do documents edit relationship properties? | With A-1b's `setRelationshipProperties` (B28): the document's tables edit a relationship's own and its kind's properties in place. B24's open question about a relationship *description* stays open, so the HLD template has no description column |
| B37 | How is a message's order in a sequence edited? | Slice V-3: a new edit `setMessageStep` rather than an option on `routeRelationshipOccurrence` (§9 proposed that). Order is not geometry, needs no base version (last writer wins, like layout) and has its own exact inverse. Moving a message changes only its step when its neighbours are stepped and in order; otherwise every message on the diagram is re-stepped in the new order, so all viewers agree |
| B38 | Where does a table row's child sequence live? | In the table section's state, `sequences: { relationshipId: diagramId }`, set in the same change that creates the diagram (two lifelines and the interaction's messages in order). V4's `generatedBy` would need a column and a back-reference; the section state already carries per-row data (ignored rows) and undoes with the document. The HLD's integrations table has `perRow: { sequence: "sequence" }`; only interaction rows get one |
| B39 | What does the sequence view draw, and which response ends an activation? | Lifelines are the diagram's top-level object occurrences, left to right by `x`; messages are occurrences of flow-kind relationships, by `step`. Interactions themselves are not drawn, only their messages. A response closes the latest open synchronous request of its interaction (a stack), so repeated calls nest correctly. Self-calls are refused, as the rules refuse self-relationships (V6 stands). Fragments (V8) and *Show as canvas* (V-6) are not built; the step table is |
| B40 | Where do patterns live, and how are they parameterised? | Slice V-4: in the metamodel package as `documentPatterns`, stored in the repository's `settings.metamodel` like `layers` (no migration) and published with the rest of the package. A string `"$template.<param>"` anywhere in a pattern's sections is replaced by the parameter (or its `default`); `null` removes the key, which is how an optional `perRow` is left out. Sections are checked against the section schema after substitution. A pattern used twice needs an explicit `prefix` (`data` makes `dataContext`), and references inside the pattern follow it; two sections with one key are refused with that hint, rather than prefixed automatically |
| B41 | How does a template extend another? | `extends` names another document type: its resolved sections come first, and this template's entries go `after` a named one or at the end. Template-level `overrides` (by section key) change `title`, `guidance`, `lock` and `allow` of a section from the base or a pattern, never its config or bindings. The subject filter is inherited unless the template sets its own. Cycles and unknown names are refused when the package loads |
| B42 | Where are an author's changes to a section kept, and what may they change? | In `definition.layout` (reserved, like `subject`): per section `hidden`, `title`, extra fact `properties`, `hiddenColumns` and added property `columns`. The projection honours each only where the section's lock and `allow` grant it, so a stale or hand-written layout cannot get round a lock. `fixed` allows content only; `configurable` (default) what `allow` lists; `free` renames and hides. Changing a free section's config entirely waits for the designer's settings forms (V-5); reordering optional sections is not built. Required sections and required columns cannot be hidden |
| B43 | How do regions store what authors add? | As full section definitions in `layout.regions[region]`, each treated as `free`, with its content under its own key (`additional1`, …). They are checked with the same `checkSection` as template sections; one that does not fit (not in the palette, a key clash, an unknown property) is skipped and listed under what is missing. Palettes offer `heading`, `prose`, `facts`, `diagramLink` and `relationTable`; a repeater or sequence link needs a row, so only templates have them |
| B44 | What do the repeater and sequence link do? | A `repeater` takes the rows of a `relationTable` section and shows, per row, child sections: `heading`, `prose`, `facts` (of the row's counterpart or, with `of: "relationship"`, of the relationship itself, edited with `setRelationshipProperties`) and `sequenceLink`. Children's state is in the repeater's key, `rows[relationshipId][childKey]`, so two authors writing two rows at once conflict on that key (accepted for now). A sequence link creates the row's interaction sequence like the table's per-row link (B38) and shares the table's when it has one, so a row never gets two. The Essentials *Integration specification* keeps sequences in its details blocks only |
| B45 | How is an element created from prose? | Besides *Create "…" as* in the `@` picker (B34), typing `@+Name` goes straight to creating: the picker shows the types the section allows and Enter creates the element and mentions it, in one change |
| B46 | How does a person make a view of each kind? | Slice U-1: one *New diagram* item everywhere (the File menu, the explorer's + button and its empty space, a row's *New ›*), opening a dialog with the types grouped by kind. It asks only what the kind needs: a document its subject (only the elements its template accepts), a sequence its first two lifelines and whether to draw the messages of their interactions, a canvas optionally an element to start around; a matrix takes its type's axes. The folder defaults to the selection's and can be changed, so no folder needs to be selected first. Shortcuts on an element create the same views around it in one change: a canvas with the element in the middle and up to 12 related elements the type allows, and a sequence of its interactions |
| B47 | Where does demo content for views live? | Slice U-2: in the shared example repository (`05-structures/example-repository.json`), so a new database, the tests and the browser tests all start from a view of every kind. Browser tests create their own elements under names the example does not use, and delete what they create |
| B48 | How do admins make a new diagram type, and what may change on one in use? | Slice U-3: only by duplicating an existing type, which copies everything (template, matrix, symbols) under a new name and key, so no type starts empty or broken. A type no diagram uses can change kind (taking the new kind's starting settings) or be deleted; a type in use keeps its kind, and `metamodelImpact` refuses a publish that changes it. Taking an element or relationship type away from a type in use is allowed: what is drawn stays, the review lists it, and nothing more of it can be added |
| B49 | What counts as a duplicate when a new object is named? | Slice D-1: the matcher normalises names (Unicode, case, accents, separators; `+`, `#`, `&` kept, so *C++* ≠ *C*) and scores reordered words, acronyms, word prefixes and trigram spelling. Only the same type with the same normalised name is *exact* and reused by default; the engine's hard rule is unchanged (B8: exact type, case-insensitive), so *claims-manager* can still be created deliberately. Related types (parent, child, sibling under the same parent) are shown as such; unrelated types only when the name is close. Open: whether family clashes should block (duplicates-and-identity.md §11) |
| B50 | Must external ids be unique? | Yes, from slice D-1: a `system: id` pair belongs to at most one live object, and to at most one live relationship, since an integration could not tell which to update. A deleted object frees its ids |
| B51 | How does a type's name policy treat levels, containers and related types? | Slice D-2: four inherited fields on the object type. `uniquePerLevel` defaults on, so *Payment* may exist once per semantic level (semantics.md §4). `container` scope is checked among objects with the same container and not at all for an object without one. `uniqueAcross: family` compares with parents, subtypes and siblings under the same parent; the policy is the new object's type's. `onClash: warn` saves with a finding. B8 stays the default (`type`) |
| B52 | Are repeated relationships refused? | No: slice D-2's `distinct` only adds a finding, shown in the toast, since the connect menu already offers the existing relationship and a repeat can be deliberate. Flows, triggers and interactions compare their payload and interaction too |
| B53 | What happens to existing repeats when a type becomes stricter? | Nothing: publishing never changes the model. The publish review counts the objects that already repeat a name, and the policy applies to their next rename or move |
| B54 | How are possible duplicates found and dismissed? | Slice D-3: the engine's `possibleDuplicates` runs where the model is loaded (the browser today), so the report is always current and needs no job; a server pass with `pg_trgm` waits until repositories outgrow it. Only related types at one semantic level are compared, and only pairs that share a name key or a neighbour. The score combines the best name match (over names and other names, without credit for one name starting another) with the share of neighbours in common, which counts in full from four shared; pairs from 75% are shown. Objects related to each other directly are never raised. *Not duplicates* is kept on both objects with both names, so either remembers it and a rename of either raises the pair again. Other names (`aliases`) arrive in D-3 rather than D-4 because detection and search need them first |
| B55 | Can admins make types from scratch, and how does someone start over? | Slice R-1, asked for when setting up a metamodel end to end. Object and relationship types are created by name (key from the name) and edited on the draft: name, plural, parent, category, level and abstract; name, both readings and meaning. A type is deleted from the draft with the rules naming it, only while nothing uses it and no type inherits from it. A new diagram type may now also start blank (a canvas showing every top-level object type), amending B48, so a metamodel with none can get its first. Starting over is a new repository (Essentials, empty, another repository's metamodel, or a file) and deleting the old one, rather than wiping a repository in place, which open sessions could not follow. The first diagram of an empty repository makes a *Diagrams* folder |
